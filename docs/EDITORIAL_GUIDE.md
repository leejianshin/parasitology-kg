# 编辑与审核规范

## 1. 文件职责

每个实体只建立一个权威Markdown文件。该文件同时包含：

- YAML front matter：供程序解析的实体、关系、来源和审核信息；
- Markdown正文：供学生阅读和语义RAG使用。

三元组、JSON和图数据库导入文件属于派生数据，不能与Markdown主数据分别手工维护。

## 2. 建立实体的条件

只有满足至少一项条件时才独立建立实体：

- 需要被多种寄生虫或关系重复引用；
- 在生活史、致病、诊断或防控中承担明确角色；
- 学生需要对其进行独立检索或比较；
- One Health分析需要跨人、动物或环境查询。

普通形容词、单次出现的描述和没有稳定边界的短语不单独建实体。

## 3. 实体命名

- 中文标签采用当前课程和权威教材中的规范名称；
- 拉丁学名保存在`scientific_name`，不用于替代稳定ID；
- 旧名、俗名、英文变体和常见误写进入`aliases`；
- 同名异物必须建立不同ID并在正文说明；
- 分类学变化不得直接删除旧称，应保留检索入口和变更记录。

## 4. 关系编写

每条关系必须：

1. 使用`schema/relation-types.yml`中的受控关系；
2. 按规定方向保存；
3. 指向已存在或在同一变更中新增的实体ID；
4. 具有可独立阅读的`statement_zh`；
5. 至少绑定一个来源和定位信息；
6. 记录关系本身的审核状态。

不得使用`related_to`一类无法说明机制的万能关系。如现有词表无法准确表达，应先提出Schema变更，而不是临时创造新谓词。

## 5. 证据处理

### direct_statement

来源直接陈述该关系。允许释义，但不能扩大主张。

### supported_inference

来源提供了足够材料，可以作出受限推断。正文必须使用“提示”“支持”“可能”等与证据强度相称的语言。

### background_only

仅用于说明背景，不得单独支撑正式关系进入`reviewed`状态。

同一结论在多个AI输出中重复，不构成多来源验证。必须回到教材、课件、论文、规范或其他原始材料。

## 6. 来源定位

优先使用：

- 教材和专著：版本、章节、页码；
- 课件：文件版本、幻灯片编号；
- 教学大纲：专业、版本、章节或条款；
- 论文：页码、表格、图或结果小节；
- 网页：页面标题、发布日期、稳定URL和访问日期。

如扫描PDF无法稳定取得页码，应记录文件页序并明确是“PDF页序”，不能伪装成印刷页码。

## 7. One Health表达

One Health应体现在可查询关系中，而不是只写总结段落：

- 人类健康：感染、疾病、诊疗和行为；
- 动物健康：宿主角色、动物感染和传染源意义；
- 环境健康：水体、土壤、媒介和生态传播条件；
- 跨部门治理：养殖、食品安全、环境卫生和多部门防控。

必须区分：

- 已确认的生活史机制；
- 流行病学关联；
- 合理但尚未验证的推断；
- 政策或教学上的防控建议。

## 8. 面向RAG的正文

- 每段尽量围绕一个清楚命题；
- 使用实体全名，减少模糊指代；
- 数字必须保留时间、地区和分母；
- 不把特殊地区数据外推为普遍事实；
- 重要否定和限制应靠近相关结论；
- 不复制大段受版权保护的教材原文；
- 不为了语言流畅而删除来源差异和不确定性。

## 9. 审核门槛

实体进入`reviewed`状态前必须确认：

- 名称和分类口径正确；
- 所有实体ID和关系合法；
- 关键关系有直接证据或明确标记的推断；
- 正文与结构化关系一致；
- One Health表达没有夸大因果；
- 学习提示与证据相符；
- 校验脚本通过；
- 学科教师完成最终确认。

## 10. 修改与废弃

- 已发布ID原则上不复用；
- 事实修订应说明原因并保留Git历史；
- 被新证据否定的关系先标记`disputed`或`deprecated`；
- Schema变化通过独立PR处理，并说明迁移影响；
- 不直接删除仍可能影响旧链接和历史解释的实体。
